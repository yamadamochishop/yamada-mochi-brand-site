# YM-008 Recipe SEO Foundation

Recipe Hub Ver.1（YM-007）の上に、レシピを継続的に増やして検索流入から購入へつなぐための
調査・設計・運用基盤をまとめる。記事本文はこのドキュメントでは確定しない。

調査日: 2026-09-02。以降の記述で「確認」と書いたものは、この日にリポジトリまたは
本番URLに対して実際に取得した結果を指す。

## 1. Scope

- 対象は `/recipes` 配下のレシピコンテンツと、そこから `/products` → BASE へ向かう導線。
- 対象外: 本番デプロイ、公開、Search Console設定、Analytics設定、価格・送料・EC変更。
- このドキュメントは Topic Cluster、優先順位、Recipe Article Standard、Human/AI境界、計測設計を確定する。
  記事の材料・分量・調理時間・食品安全に関する記述は、すべて Human 確認を経てから `data/recipes.ts` に入る。

### 2.2 旧レシピ本文の性質（確認済み）

Internet Archive から旧レシピ本文を取得したところ、1本あたり材料4〜7行、手順2〜4行で、
本文全体が数百文字にとどまる。写真はアーカイブに残っていない。

したがって旧記事は「そのまま復活させる資産」ではない。価値があるのは**題材リスト**の方で、
山田もち店が自ら公開していた食べ方14種（餅10・漬物2・米/米粉2）が分かる点にある。
本文・分量・手順は5〜6年前のもので、再公開の前に Human 確認が必要である。

## 3. Search / SERP findings

検索ボリュームは取得できていない。以下は SERP の構成・競合の被覆状況・検索意図からの相対評価であり、
数値としての需要推定ではない。

### 3.1 ヘッドクエリは大手レシピメディアが占有している

「餅 アレンジ」「余った餅 レシピ」「切り餅 レシピ」系のSERPは、Nadia・クラシル・macaroni・
デリッシュキッチン・クックパッド・味の素パーク、およびメーカーのオウンドメディア（ニチレイ、ノーリツ）が
上位を占める。いずれも「35選」「40選」「60選」形式のまとめで、レシピ数と被リンクで勝負する領域である。

**この領域を正面から狙わない。** 6商品の餅屋がレシピ数で勝てる見込みがなく、勝てても
「レシピを見て他社の餅を買う」読者を集めるだけで購入につながらない。

### 3.2 一方で、専門店が上位に入っている領域がある

- 「餅 硬くなった 柔らかくする」では、餅なげ.net（浜松の餅店）のコラムが上位に現れる。
- 「たまり餅」では、飛騨高山のたまり餅が「みたらし団子に近い醤油味の飛騨のもち」として
  食べチョク・地元小売の商品ページ経由で説明されている。
- 「たかやまもち」は岐阜県独自のもち品種で、JA全農岐阜が品種特性を公開している。
  「粒がしまり、甘み・粘り・白さがある」等の特性が公的資料として存在する。

つまり **「餅そのものの扱い方」と「品種・味の固有名詞」** は、作り手が書くほうが自然な領域であり、
大手まとめ記事が薄い。

### 3.3 明確な空白

| テーマ           | SERPの状態                                                                     |
| ---------------- | ------------------------------------------------------------------------------ |
| 昆布餅           | 専用の解説がほぼ無い。かき餅の材料として言及される程度                         |
| 黒ごま海老餅     | 「えび餅」は関東の桜えび餅・岩手宮城の食べ方が出るが、黒ごま海老餅の解説は無い |
| たまり餅         | 商品ページはあるが、由来・味・食べ方を説明した記事が無い                       |
| 味付き餅の食べ方 | 「味がついている餅は何をつければいいか」に答える記事が無い                     |

山田もち店はこの4種すべてを製造・販売している。**ここが最も明確な競争優位である。**

### 3.4 地域・郷土の軸

- 飛騨雑煮／岐阜のお雑煮（角餅・すまし・正月菜）は名前のついた郷土料理として記述が存在する。
- 漬物ステーキは飛騨の郷土料理としてWikipedia・岐阜県観光公式・dancyu・飛騨企業が扱う。
  競合は中程度以上。ただし正統な作り方は**白菜の漬物**が主で、山田もち店は白菜漬けを
  `data/` に持たない（2.3参照）。赤かぶで書けるかは Human 確認事項。

### 3.5 季節性

- 12〜1月に集中する需要（余った餅、雑煮、焼き方）と、通年需要（保存、硬くなった餅、
  味付き餅の食べ方）が分かれる。
- 通年テーマを先に積むほうが、年末だけの流入に依存しない構造になる。

## 4. Competitive opportunity

勝てる根拠を3つに整理する。

1. **一次情報**: 自家栽培「たかやまもち」を育て、搗き、朝市で売っている。品種特性・製法・
   保存の実際を一次情報として書ける。大手まとめ記事は書けない。
2. **固有商品**: 昆布餅・たまり餅・黒ごま海老餅・三色豆餅は、検索結果に解説が存在しない。
   商品名がそのまま検索語になり、答えられるのが製造者しかいない。
3. **地域**: 飛騨高山・陣屋前朝市という具体的な場所と、飛騨雑煮・漬物ステーキという郷土料理。

逆に、次は狙わない。

- 「餅 レシピ 30選」型のまとめ。
- 山田もち店の商品と接続しない餅レシピ（他社の切り餅で成立する一般アレンジ）。
- もち米・もち米玄米・米粉のレシピ（2.3のとおり売る商品が無い）。

## 5. Topic Cluster

Pillar は既存の `/recipes` を使う。新規Pillarページは作らない。

```
Pillar: /recipes （お餅のレシピ）
├─ Cluster A: 餅の扱い方（通年・技術）
│   焼き方 / 温め方 / 硬くなった餅 / 保存・冷凍 / 失敗の直し方
├─ Cluster B: 味ごとの食べ方（固有商品・独自性最大）
│   昆布餅 / たまり餅 / 黒ごま海老餅 / 三色豆餅 / 草餅 / プレーン
├─ Cluster C: 場面別（需要の受け皿）
│   朝ごはん / おつまみ / おやつ / 食事のおかず
└─ Cluster D: 飛騨の餅（地域・季節）
    飛騨雑煮 / 朝市の餅 / 年末年始 / 漬物と餅
```

Cluster B が最優先である。理由は、独自性・購入接続・競合の薄さの3つが同時に成立する唯一の
クラスタだからで、検索数の推定によるものではない。

Cluster A は購入接続が弱いかわりに通年で流入し、内部リンクで B へ送る役割を持つ。
既存の「お餅のおいしい焼き方」がすでに A のハブとして機能している。

## 7. Recipe Article Standard

`RecipeRecord`（`types/content-model.ts`）がそのまま記事の型である。新しいスキーマは作らない。

### 7.1 必須／任意／禁止

| 区分     | 項目                                                                                                                              |
| -------- | --------------------------------------------------------------------------------------------------------------------------------- |
| 必須     | `title` `slug` `description` `category` `ingredients`（名前+分量） `steps`（1始まり連番） `relatedProductIds`（1件以上） `status` |
| 推奨     | `seo.title` `seo.description` `seo.canonicalPath` `notes` `variations` `column`                                                   |
| 条件付き | `mainImage`（撮影後。登録すると `Recipe` JSON-LD が有効になる） `stepImages`                                                      |
| 人間確認 | `servings` `cookingTimeMinutes` `allergens` `storageNotes`                                                                        |

`servings` と `cookingTimeMinutes` は、Human が実際に作って計測した場合にだけ設定する。
YM-007 の判断を維持する。**推測で埋めない。**

### 7.2 AI生成レシピで起きやすい事故と、その防ぎ方

| 事故                       | 防ぎ方                                                                                    | 実装状況                         |
| -------------------------- | ----------------------------------------------------------------------------------------- | -------------------------------- |
| 試していない調理時間の断定 | `cookingTimeMinutes` を任意にし、未確認なら未設定。設定時は正の整数を強制                 | 型 + `validateContentModel`      |
| 人数・分量の捏造           | `servings` を任意にし、未確認なら未設定                                                   | 型（YM-007）                     |
| 手順の抜け・番号ずれ       | `steps` の `position` が1始まり連番であることを検証                                       | `validateContentModel`（YM-008） |
| 材料の分量欠落             | 材料に名前と分量の両方を要求。同名材料の重複を検出                                        | `validateContentModel`（YM-008） |
| 食品安全情報の誤り         | アレルゲン・賞味期限・保存は商品ページ（`data/catalog.ts`）を正本とし、レシピ側で書かない | 運用ルール + Human Gate          |
| 存在しない商品への言及     | `relatedProductIds` はカタログ実在IDのみ。1件以上を必須化                                 | `validateContentModel`           |
| 無関係なCTA                | CTAは `relatedProductIds` から自動生成（`RecipeProductCta`）。手書きしない                | `app/recipes/[slug]/page.tsx`    |
| 写真と工程の不一致         | 画像は `stepImages`／`step.image` に紐づけ、alt必須                                       | `validateContentModel`（YM-008） |
| canonicalの取り違え        | `seo.canonicalPath` が `/recipes/<slug>` と一致することを検証                             | `validateContentModel`（YM-008） |
| キーワード詰め込み         | `seo.title`／`description` は本文の要約であることを SK-005 レビューで確認                 | Human/AI レビュー                |
| 他サイトの焼き直し         | 出典は山田家の実践のみ。外部レシピを参照しない                                            | 運用ルール（SK-004 準拠）        |
| 根拠のない「おすすめ」     | 味の推奨は `column`／`variations` に置き、事実（手順）と分離                              | 型の分離（YM-007）               |

### 7.3 記事構成

詳細ページのレンダリング順は `app/recipes/[slug]/page.tsx` が固定しており、記事側で変えない。

```
H1 レシピ名
   description（1〜2文。何をどうする料理か）
   [mainImage]
   使うお餅（relatedProductIds から自動）
H2 材料 …… 名前 + 分量
H2 作り方 …… 1始まりの連番
H2 おいしく作るポイント（notes、任意）
H2 アレンジ（variations、任意）
H2 コラム（column、任意。暮らしの話。調理手順を入れない）
   CTA（relatedProductIds から自動 → BASE）
H2 ほかのレシピ（自動、最大3件）
```

FAQ は現状のレシピ詳細に枠が無い。必要になった時点で `RecipeRecord` の拡張として扱い、
記事本文に見出しだけ足す運用はしない。

### 7.4 画像要件

| 項目         | 要件                                                                |
| ------------ | ------------------------------------------------------------------- |
| `mainImage`  | 4:3 以上の横位置。完成した料理が主題。`role: 'primary'`             |
| `stepImages` | 失敗しやすい工程だけ。全工程を撮る必要はない。`role: 'recipe_step'` |
| alt          | 必須。何が写っているかを書く。商品名の羅列にしない                  |
| 撮影の原則   | 実際に作ったものを撮る。生成画像・他媒体の写真を使わない            |
| 未撮影時     | 画像要素もプレースホルダも出さない（YM-003B / YM-007 の方針を維持） |

## 8. SEO / structured data requirements

既存実装を変えない範囲での要件。

| 項目                | 現状                                         | 要件                                              |
| ------------------- | -------------------------------------------- | ------------------------------------------------- |
| canonical           | 自己参照（`alternates.canonical`）           | 維持。`seo.canonicalPath` と一致（検証済み）      |
| title / description | `seo` があれば優先、無ければ本文から         | 記事ごとに `seo` を書く                           |
| OGP                 | `mainImage` があればページ固有、無ければ既定 | 撮影後に自動でページ固有になる                    |
| `BreadcrumbList`    | hub・詳細の両方に出力                        | 維持。可視パンくずは未実装（YM-007 の follow-up） |
| `ItemList`          | hub にタイトルのみ                           | `url` の追加は YM-007 の follow-up のまま         |
| `Recipe`            | `mainImage` がある時のみ出力                 | 維持。**画像なしで出力しない**                    |
| `prepTime` 他       | 出力しない                                   | 維持。`seo-safety.test.mts` が不在を検証している  |
| sitemap             | `publishedRecipes` から自動                  | `status: 'published'` にした時点で自動追加        |

`Recipe` 構造化データに `recipeYield` `totalTime` `nutrition` を足さない。
Human が計測していない値をマークアップに入れることになるためで、これは
`tests/seo-safety.test.mts` が守っている制約である。

## 9. Internal linking strategy

| --------------- | ---------------------------------------- | --------------------------- |
| 商品 → レシピ   | `getRecipesForProduct`                   | 2件（購入導線を圧迫しない） |

新規レシピを1件足すと、この5経路すべてが自動で更新される。**手書きの内部リンク表を作らない。**

Cluster A（扱い方）の記事は `relatedProductIds` に全6商品を入れると、
`appliesToEveryProduct` 判定により商品個別CTAではなく商品一覧CTAになる

Cluster A の新規記事はこの形に揃える。

## 10. Human / AI workflow

```
AI      検索・SERP調査 → テーマ選定 → Recipe Brief 作成
        ↓
Human   ── Gate 1: テーマとBriefの承認 ────────────────
        ↓
Human   実際に調理 → 味・分量・時間を確認 → 撮影
        ↓
Human   ── Gate 2: 材料・分量・手順・調理時間・食品安全の確定 ──
        ↓
AI      RecipeRecord へ起こす → seo/内部リンク/構造化データ → self-check
        ↓
AI/人間 ── Gate 3: 独立レビュー（SK-005 または人間） ──────
        ↓
Human   ── Gate 4: main マージ・公開 ──────────────────
        ↓
AI      公開後の計測 → 改善提案
```

自動化してよいのは、調査・構成・原案・データ整形・SEOチェック・計測の整理まで。

自動化してはいけないのは次の4点で、いずれも「AIが確認できないこと」である。

1. 材料の分量と調理時間の確定（作らないと分からない）
2. 食品安全・アレルゲン・保存に関する記述の確定（誤ると健康被害になる）
3. 味の評価・おすすめの確定（食べないと言えない）
4. 公開の判断

`status: 'draft'` のレシピはルート・一覧・サイトマップのいずれにも現れない（YM-007）。
Gate 2 を通るまで `draft` のままにすることで、未検証レシピが公開される経路を塞げる。

## 12. Measurement / improvement loop

**現時点で Search Console はこのリポジトリに接続されていない。** 検証タグもエクスポートも存在しない。
以下は「接続された場合の設計」であり、現在動いている計測ではない。

### 12.1 いま取れるもの（GA4のみ）

| 指標                     | 取得方法                                       |
| ------------------------ | ---------------------------------------------- |
| レシピページの表示       | GA4 page_view                                  |
| レシピ経由のBASE遷移     | `trackBaseClick('recipe_product')`（実装済み） |
| 記事CTA経由のBASE遷移    | `trackBaseClick('article_cta')`                |
| 商品ページ経由のBASE遷移 | `trackBaseClick('product_detail')`             |

`recipe_product` placement は YM-007 で分離済みなので、レシピ由来の購入意図を
商品カードや記事CTAと混ぜずに見られる。

### 12.2 接続後に取るもの（将来候補・未接続）

impressions / clicks / CTR / average position / indexed 状態 / query / landing page。
接続は Search Console 側の設定変更にあたり、**Human Gate**。このリポジトリからは行わない。

### 12.3 ループ

```
公開 → 4週待つ（インデックスと季節変動を吸収）
     → GA4のBASE遷移とページ表示を確認
     → （GSC接続後）query と position を確認
     → 改善候補を SK-003 で順位付け
     → title/description・内部リンク・CTA の順に、本文編集より低リスクな手段を先に試す
     → 再計測
```

再計測の窓（4週）の中で同じページを変更しない。SK-003 の
`Existing experiment / Wait for measurement` の扱いに従う。

## 13. Risks

| リスク                                   | 対応                                                     |
| ---------------------------------------- | -------------------------------------------------------- |
| 未検証レシピが公開される                 | `status: 'draft'` を既定にし、Gate 2 を通るまで上げない  |
| 写真が撮れずレシピだけ増える             | `Recipe` JSON-LD が出ないまま記事だけ増える。P0 #1 が先  |
| 商品と関係の薄いレシピが増える           | `relatedProductIds` 1件以上を必須化（実装済み）          |
| 旧レシピURLの404が残る                   | Search Console データを得てから判断（Human Gate）        |
| 季節商品レシピが販売期間外に残る         | `availabilityStatus` と `salesPeriod` を確認してから公開 |
| 食品安全の記述を推測で書く               | 商品ページを正本とし、レシピ側に書かない                 |
| 大手まとめ記事と正面衝突して成果が出ない | Cluster B を優先し、まとめ型記事を作らない               |
